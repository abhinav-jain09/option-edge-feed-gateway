# Order chart history over the existing gateway socket

Draft implementation for part of OP-P4-02, coordinated with web reconciliation PR1546. OP-P4-01 and the rest of OP-P4-02 remain incomplete. There is no new Kafka reader, REST endpoint, service or Jenkins stage.

A registered, admitted socket receives `order-chart-history-hello` with schemaVersion1, available resources and maximum16 records. This is a transport capability only. The client must still wait for the existing auction/CVD/footprint readiness hello; capability never means a partially hydrated cache is complete. Auction reads also check hydration under the existing incarnation lock, through the atomic page read. Writes occur after releasing that lock.

Request type and response type are `order-chart-history`. Each request includes schemaVersion1, an opaque string requestId of at most64 characters, resource, canonical sessionDate and cursor. Auction uses textual `after` as an inclusive minute, empty for the first page. Footprint uses timeframe1m/5m/15m, exclusive integer `after` epoch milliseconds and inclusive `toMs`; both are validated within the requested futures session. Requests are limited to1024 UTF-8 bytes by the existing socket dispatcher. Unknown/unregistered sockets cannot use this path.

Replies echo requestId, resource and sessionDate and contain records, nextCursor and done. Admission schemas and source records remain unchanged. A page reads at most16 records. Its response budget is the smaller of512KiB and one quarter of the existing outbound queue budget. Oversized pages are re-read with a halved count; a single record that cannot fit returns record_budget without advancing a cursor. Errors never report done or advance history. Existing four-permit backfill admission and bounded asynchronous writer remain in use. Busy/loading errors preserve the request generation.

This is paged bootstrap, not durable event replay or a frozen multi-page snapshot. The client must preserve its existing live-update/correction barrier across interleaved history pages, reject stale request generations, and retain admitted data on viewport changes. Client integration is still pending. Older gateways omit the capability and require the existing REST bootstrap fallback. Versioned live delta-flow, absorption path, VWAP and signal delivery remains separate work; this draft does not claim stream-only completion.

Footprint hydration is now guarded by OrderChartReplayGate. The cache consumer closes the gate before its actual footprint-bar cache-window seek, captures each partition end offset, and opens it only after applied positions reach all captured offsets. Late partitions reopen the gate without dropping prior barriers; retries replace ownership, unassigned partitions and failed seeks remain loading, and recovery invalidates the old attempt. The socket holds the same gate monitor through its snapshot read. Capabilities remain separate from readiness.
